\chapter{Architecture}
\section{Ecosystem}
The system is composed of an \textbf{IoT Network} and a \textbf{Cloud Application}. 

The \textit{IoT Network} consists of a \textbf{Border Router} and a set of \textbf{3D Printers}, each connected to a set of \textbf{Sensors}.

The \textit{Cloud Application} serves as the central orchestration hub of the \textbf{\textit{Eco3DPrint} ecosystem}, coordinating communication between the distributed hardware nodes and the \textbf{User App interface}. 

\section{IoT Network}
\subsection{Protocol Stack}
The communication architecture implements a specialized multi-layered stack to bridge physical sensors with the cloud. At the base, \textbf{IEEE 802.15.4} provides the low-power radio foundation, while the \textbf{6LoWPAN} adaptation layer compresses headers to allow \textbf{IPv6} traffic over constrained links. Networking is maintained by \textbf{RPL} (Routing Protocol for Low-Power and Lossy Networks), which constructs dynamic routing paths to ensure data reaches the gateway even in lossy wireless environments.

\medspace

The application layer is split according to functional requirements. \textbf{CoAP} (Constrained Application Protocol) is used for control-plane operations, including node registration, health monitoring, and reliable block-wise transfer of \textbf{STL files}, following a lightweight request–response model. It runs over \textbf{UDP} (User Datagram Protocol), a connectionless transport protocol that minimizes overhead and latency but does not guarantee delivery or ordering. In contrast, \textbf{MQTT} (Message Queuing Telemetry Transport) provides a dedicated telemetry channel based on a publish–subscribe architecture to stream high-frequency vibration and voltage data for real-time Machine Learning inference. It operates over \textbf{TCP} (Transmission Control Protocol), a connection-oriented transport protocol that ensures reliable, ordered, and error-checked delivery of data streams. 

\medspace

The system utilizes \textbf{JSON} (JavaScript Object Notation) as the primary data encoding format for control and telemetry messages. For the transmission of 3D models, the application implements a \textbf{CoAP Block-wise (Block1) transfer mechanism}.

\subsection{Nodes}
The architecture of the IoT Network is divided into two dedicated node types that operate as a coordinated local pair: \textit{Actuator Nodes} and \textit{Sensor Nodes}:
\begin{itemize}
	\item \textbf{Actuator Nodes (Smart Printers):} These nodes execute the primary 3D Printer state machine, managing initialization, network synchronization, and simulated printing operations. Acting as CoAP servers, they receive administrative traffic and ingest large STL models using block-wise transfers. Each node hosts a localized Machine Learning inference engine that subscribes to paired sensor telemetry, extracts statistical features from incoming data, and autonomously halts the printing process when consecutive anomalies are detected to reduce resource and energy waste.
	\item \textbf{Sensor Nodes (Smart Sensors):} These nodes isolate telemetry acquisition from mechanical control processes by operating under a separate state machine. They simulate physical telemetry streams (including acceleration, filament tension, and power consumption) using Gaussian-based models representing both normal and faulty behavior. Telemetry is encoded as SenML-compliant JSON and transmitted over MQTT. To conserve constrained radio resources, transmissions are batched in groups of five messages, after which sampling pauses until a CoAP CONT or STOP command is received from the paired printer. 
\end{itemize}

\section{Cloud Application}
\subsection{Backend}
The \textbf{Cloud Application backend} is built on a multi-threaded Python architecture, and it bridges the resource-constrained IoT network with the graphical User Application (the frontend). The backend is strictly \textbf{modular}, separating network communication, business logic, and data persistence into dedicated functional components. 
\begin{itemize}
	\item \textbf{Database Access Layer:} Manages persistent data storage in a MySQL database, utilizing Connection Pooling to safely handle concurrent, thread-safe read and write operations;
	\item \textbf{CoAP Server:} Runs over UDP/IPv6 to handle low-frequency control events, including node registration, end-of-print notifications, and shutdown signals. It is implemented using \textbf{CoAPthon} \cite{coapthon};
	\item \textbf{MQTT Handler:} Runs as a background subscriber to continuously ingest high-frequency JSON telemetry (vibration and voltage data) during active prints, mapping the data directly to the database. It is implemented using \textbf{Paho} \cite{paho}; 
	\item \textbf{Node Monitor:} Maintains real-time fleet health by concurrently pinging active nodes via CoAP /health requests every 60 seconds. It utilizes an Observer pattern to instantly broadcast state changes (\textit{OFFLINE}, \textit{ONLINE}, \textit{PRINTING}) across the system;
	\item \textbf{Print Manager:} Orchestrates the print job queue and handles the reliable transmission of 3D models. It utilizes CoAP Block-wise transfer to partition and sequentially send large binary STL files to available nodes;
	\item \textbf{WebSocket Manager:} It pushes live node status updates to the User App's dashboard and processes complex analytical requests to generate daily, weekly, and monthly energy reports.
\end{itemize}

\subsection{Frontend}
The \textbf{Frontend Application} (\textbf{User App}) is a desktop-based graphical interface built using the Python \textbf{tkinter framework} \cite{tkinter}. A background daemon thread runs an asyncio event loop for a persistent, non-blocking WebSocket. Messages move through a thread-safe queue to the main GUI, which polls and routes them to the appropriate screen based on their type:
\begin{itemize}
	\item \textbf{3D Printers Dashboard:} Displays a responsive grid of interactive cards for real-time fleet management. It dynamically applies color filters to printer icons to reflect current operational states (\textit{OFFLINE}, \textit{ONLINE}, \textit{PRINTING}) and includes modal dialogs for viewing node details and queueing STL files;
	\item \textbf{Daily Report:} Visualizes the current day's energy metrics, automatically converting raw Joules to kWh. It features high-level global summary cards and scrollable tables (ttk.Treeview) that break down well-used versus wasted energy by individual printer and STL file;
	\item \textbf{Weekly Report:} Aggregates telemetry over the week. It implements a zero-padded data structure to ensure consistent daily rendering and utilizes multiple centered tables to highlight energy consumption trends throughout the week;
	\item \textbf{Monthly Report:} Provides a long-term analytical view with a Year-To-Date (YTD) summary. It displays a month-by-month historical table tracking total print volume, successful energy usage, and energy lost to anomalies.
\end{itemize}

\section{Project Alignment}
\subsection{Project Objective}
\begin{quote}
	\textbf{Smart Homes and Buildings:} enabling real-time control and energy efficiency in residential or commercial environments.
\end{quote}

I choose "\textit{Smart Homes and Buildings}" as a domain for my project. I have enabled a \textbf{real-time monitoring application} where I monitor the status of the printers, create a list of STLs to print in real time and monitor the energy consumption of the printers. All of this is \textbf{designed to monitor energy efficiency}, supported by a \textbf{Machine Learning model} that proactively halts faulty prints before they occur. This system is primarily intended for \textbf{commercial environments} where multiple 3D Printers operate simultaneously, such as print farms or production labs, where efficiency, reliability, and cost control are critical. However, it is equally applicable in advanced home setups with multiple 3D Printers, offering the same benefits of centralized monitoring, energy optimization, and failure prevention on a smaller scale. 

\subsection{Application Protocol}
The architecture implements a hybrid application layer utilizing both \textbf{CoAP} and \textbf{MQTT} to establish a clear distinction between the control and telemetry planes across the cloud ecosystem and the decoupled edge nodes. 

\medspace

\textbf{CoAP} serves as the primary mechanism for all control-plane operations, spanning both cloud-to-device and device-to-device interactions. In this architecture, CoAP was selected over MQTT for discrete control tasks due to the following specific reasons:
\begin{itemize}
	\item \textbf{RESTful Interaction for Cloud Management:} Unlike the publish-subscribe model of MQTT, CoAP is a request-response protocol operating over lightweight UDP. This allows the Actuator node to execute initial cloud registration and status reporting without maintaining a persistent, energy-intensive connection during long idle periods, significantly improving fleet energy efficiency;
	\item \textbf{Reliable Block-Wise File Transfer:} CoAP inherently supports Block-wise transfers (Block1). This mechanism is uniquely optimized for sending large binary assets like STL models from the cloud backend to resource-constrained edge nodes one fragment at a time, preventing RAM exhaustion;
	\item \textbf{Reduced Protocol Overhead and Local Pacing:} By eliminating the heavy overhead of the TCP three-way handshake, CoAP minimizes radio transmissions for occasional administrative tasks. Crucially, this efficiency is extended to the local network: the decoupled Actuator and Sensor nodes utilize local CoAP resources for asynchronous pairing discovery and for a strict, synchronous ``Ping-Pong'' control loop, where the Actuator sends low-overhead commands (\texttt{START}, \texttt{CONT}, \texttt{STOP}) to dynamically pace or halt the sensor's sampling states based on ML inference cycles.
\end{itemize}

In contrast, \textbf{MQTT} is utilized exclusively to manage the high-frequency telemetry plane during active printing phases, operating as a distributed publish-subscribe link between the edge components. Because the active printing phase already represents peak power consumption for the hardware, the additional connection-oriented TCP overhead of MQTT is relatively negligible compared to the physical operation of the machines. 

\newpage

Furthermore, a \textbf{Publish–Subscribe model is more efficient for this telemetry plane than a Request–Response approach}. The Sensor node functions as a dedicated publisher, streaming serialized multi-axis acceleration, tension, and voltage profiles to an IP-specific topic (\texttt{<sensor\_ip>/print/measurements}). The Actuator node (the printer) acts as a local subscriber, continuously ingesting this JSON telemetry stream directly from the broker to feed its localized sliding-window Machine Learning model. Once a print job concludes or is autonomously aborted due to consecutive anomalies, the nodes immediately suspend their MQTT activities.

\subsection{Edge Intelligence and Autonomous Decision-Making}
The system executes a localized \textbf{Machine Learning model} directly on the constrained \textbf{Actuator node}, enabling real-time anomaly detection without cloud dependence. In this decoupled architecture, the \textbf{Sensor node} handles high-frequency telemetry acquisition and streams raw metrics over the local network. The Actuator processes these streams locally through a C-based edge pipeline that extracts 35 statistical features from sliding data windows, significantly reducing bandwidth usage. This design also allows the Actuator to autonomously halt printing operations and issue direct CoAP shutdown commands to the Sensor node. 

\subsection{Hardware Interaction}
The project strictly adheres to the mandatory button and LED interaction requirements. 

A \textbf{physical button} is used for manual overrides, system resets, and confirming print completions, ensuring a human-in-the-loop safety mechanism. 

At the same time, \textbf{LEDs} provide essential visual feedback through color coding, yellow for initialization, green for online status, and red for failure, allowing an on-site operator to quickly assess device status without a display. 

\subsection{Data Encoding}
\textbf{JSON}, structured via the \textbf{SenML} (Sensor Measurement Lists \cite{senml}) data model, is the optimal encoding choice because its minimalist key-value structure drastically reduces packet overhead compared to the verbose tagging required by XML. This standardized approach facilitates a seamless data pipeline between the C-based firmware and the Python backend without the heavy memory or CPU requirements of an XML DOM parser.

\medspace 

For the transmission of STL models, the system implements \textbf{CoAP Block-wise transfer} to overcome hardware link limitations by partitioning binary data into sequential 64-byte chunks. This mechanism ensures reliable delivery through application-layer acknowledgments and prevents RAM exhaustion on the constrained nRF52840 nodes by processing only one fragment at a time.
